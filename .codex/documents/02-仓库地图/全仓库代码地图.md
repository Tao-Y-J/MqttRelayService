## 2. 核心数据流

```
 客户端发布消息
  → MqttBrokerHost.OnInterceptingPublishAsync（轻量：先入队判断，客户端原始发布设置 ProcessPublish=false）
     → 已识别为服务端注入（x-relay-message-id）→ 保留 Broker 默认分发
     → 无来源标识（ClientId 为空）→ 阻断默认分发并丢弃
     → 停机排空期（_acceptingClientPublishes=false）→ 阻断默认分发并丢弃
     → InMemoryMessageQueue.EnqueueAsync（有界 Channel，满载显式丢弃；异常时不回落到 Broker 默认分发）
  → MessageDeliveryService.ConsumeLoop（消费者专用线程同步循环）
    → ReadAllAsync（ChannelReader 异步挂起等待）
    → MessageRouter.RouteAsync（仅做 Topic 匹配与发送方过滤，异常向上传播）
    → MessageDeliveryService.TryForwardAsync（Retain=true 且无匹配订阅者时同样注入 Broker）
    → IMqttBrokerHost.PublishAsync（InjectApplicationMessage 单次注入，始终附加 x-relay-message-id，有来源时附加 x-source-client-id）
    → MqttBrokerHost.OnInterceptingOutboundPacketAsync（出站拦截：EchoToSender=false 时阻止回发发送方）
    → 成功：状态=Succeeded / 失败：退避等待 → 重新入队 → 死信
```

## 5. 关键设计决策

### 5.1 消息注入 + 出站拦截（非客户端直投）

当前 MQTTnet 5.x 的 `InjectApplicationMessage` 是按 Topic 广播，无法严格按 ClientId 定向投递。因此采用：
- `MessageRouter.RouteAsync` 过滤匹配客户端（路由层过滤发送方）
- `MessageDeliveryService` 单次调用 `PublishAsync` 注入 Topic
- `MqttBrokerHost` 出站拦截器 `InterceptingOutboundPacketAsync` 阻止回发发送方（Broker 分发层二次保险）
- 所有服务端注入都通过 MQTT 5.0 `UserProperties` 附加 `x-relay-message-id`（即使没有 sourceClientId 也附加），发布拦截器据此稳定区分"服务端注入"与"客户端原始发布"
- 有来源客户端时额外附加 `x-source-client-id`

注入消息 ID 由 `MqttBrokerHost._injectedMessageIds` 跟踪，容量上限 `MaxInjectedMessageIdTracking = 50000`；达到上限时一次性清空字典恢复服务并记录 Error，清空后本轮生命周期内的注入消息无法被 `EchoToSender` 出站拦截识别。

### 5.2 多消费者并发

`MessageDeliveryService.StartAsync` 根据 `ReliabilityOptions.MaxConcurrentHandlers` 启动对应数量的消费者（最小值为 1），并按 `ThroughputController.MaxConcurrencyHardLimit` 收敛上限，避免配置值大于硬上限时创建大量空转消费者。

消费者由 `StartConsumerThread` 以 `TaskCreationOptions.LongRunning` 启动到**专用线程**，消费循环 `ConsumeLoop` 是同步方法：它阻塞在 `IMessageQueue.TryDequeueBlocking` 的取件信号上，单条消息处理用 `GetAwaiter().GetResult()` 同步等待。这样取件唤醒由入队方直接释放信号完成，不经过线程池续体——否则线程池被阻塞型工作（例如管理面审计库查询）占满时，取件延迟会被拖到数百毫秒甚至数秒，而 Broker 接收路径（socket 接收循环 / IOCP 完成线程）不受影响，表现为「入队稳定、消费者掉队」。

运行期转发失败后，通过 `ScheduleRetryEnqueueAsync` 将退避延迟和重新入队调度到后台任务执行，当前消费者立即返回处理后续消息，不会被退避延迟阻塞。后台重试调度任务受 `ReliabilityOptions.MaxPendingRetryTasks` 限制（配置值小于 1 时回退到 `QueueCapacity`），超限消息直接进入死信，避免失败洪峰绕过有界队列造成无界内存增长。停机排空阶段则使用 `DelayAndRequeueDuringStopAsync` 同步等待退避结束后再重新入队，以保证排空不会在消息重新出现之前提前结束。

Retained Message 的 `Retain` 标志从 `MqttBrokerHost.OnInterceptingPublishAsync` 写入 `RouteContext`，由 `MessageDeliveryService` 传给 `IMqttBrokerHost.PublishAsync` 并在 Broker 注入时恢复。`Retain=true` 且当前没有匹配订阅者时，`MessageDeliveryService.TryForwardAsync` 仍会注入 Broker，让 MQTTnet 保存运行期内存 retained 消息；服务进程重启后 retained 消息不会恢复。`MessageRouter` 没有 Retain 分支，路由只负责 Topic 匹配与发送方过滤。

### 5.3 停机排空（多轮收敛）

`MessageDeliveryService.StopAsync` 按以下顺序执行：

1. 调用 `IMqttBrokerHost.StopAcceptingClientPublishes()` 封堵客户端新发布入口，Broker 本身保持运行
2. 取消 `_cts`，消费者循环的阻塞取件等待被取消而退出，等待消费者退出（`ConsumerShutdownWaitTimeoutMs = 2000`，消费者取消时会把在途消息保留回队列）
3. 等待后台重试调度任务收敛（`RetrySettlementWaitTimeoutMs = 2000`）
4. 多轮收敛排空：使用 `DrainQueueRoundAsync` 以 `TryDequeueAsync` 非阻塞消费当前可见消息；若仍有未退出的消费者，则用剩余排空预算等待其退出并再次 drain，直到「队列空且消费者全部退出」或 `ShutdownDrainTimeoutMs` 耗尽
5. 记录排空计数与剩余数量

`_isStopping` 期间的失败消息走同步退避重试重新入队而非后台调度，保证排空不会在消息重新出现之前提前结束。

停机/异常恢复路径上的入队与死信写入统一使用 `ShutdownForceTimeoutMs = 5000` 的强制超时，避免队列满载时使用 `CancellationToken.None` 无限阻塞停机流程。

### 5.4 队列满载策略

统一使用 `BoundedChannelFullMode.Wait`，避免 `DropWrite` 导致 `TryWrite` 返回 `true` 但消息被静默丢弃。

`DropWhenQueueFull=true` 时：应用层显式检查 `Count >= Capacity`，满则返回 `false` 并记录 Warning。

`InMemoryMessageQueue.EnqueueAsync` 区分两种取消语义：调用方主动取消时向上抛 `OperationCanceledException`；入队等待超过 `EnqueueTimeoutMs` 时记录 Warning 并返回 `false`。这一区分保证停机路径不会把本该保留的消息误判为"队列满载丢弃"而写成死信。

`InMemoryMessageQueue` 在每次成功入队后释放一次 `_itemsAvailable` 取件信号，供专用消费者线程同步阻塞取件。排空路径用 `TryDequeueAsync` 取走消息会留下多余信号，`TryDequeueBlocking` 的「先 `TryRead` 再 `Wait`」循环会把多余信号消耗掉并继续等待，既不空转也不丢唤醒。

### 5.5 客户端发布拦截失败语义

`MqttBrokerHost.OnInterceptingPublishAsync` 的处理顺序：

1. 命中 `x-relay-message-id` 跟踪字典 → 判定为服务端注入，保留 Broker 默认分发
2. `ClientId` 为空 → 阻断默认分发并记录 Warning（无来源标识的发布无法归属任何会话，转发会丢失 SourceClientId，且可能形成转发循环）
3. `_acceptingClientPublishes == false`（停机排空期）→ 阻断默认分发并记录 Warning
4. 客户端原始发布先设置 `ProcessPublish=false`，再执行活动时间更新、Payload 转换和入队

拦截链路发生异常时，消息不会回落到 Broker 默认分发路径，避免绕过内部队列、重试、死信和 `EchoToSender` 控制。

### 5.6 客户端会话快照

`ClientRegistry` 内部仍使用 `ConcurrentDictionary` 管理在线客户端，写入和更新订阅时只修改注册表内部对象；`GetSessionAsync` 和 `GetAllSessionsAsync` 返回会话快照，路由线程枚举的是独立 `HashSet`，不会与订阅事件并发修改同一个集合。

`MqttBrokerHost.OnClientConnectedAsync` 会为每次连接生成 `ConnectionId` 并写入 MQTTnet `SessionItems`，`OnClientDisconnectedAsync` 注销时带回该值。`ClientRegistry.UnregisterAsync` 只移除与当前 `ConnectionId` 匹配的会话：`connectionId` 为空时只记 Warning 并保留会话（不删除），与当前会话 `ConnectionId` 不一致时记 Warning 后忽略，旧连接的延迟断开事件不会误删同 `ClientId` 的新连接。`UpdateActivityAsync` 对空标识做前置守卫，并用顶层 try/catch 兜底：活动时间属于纯记账操作，记账异常不得导致发布消息被丢弃。

### 5.7 BrokerWorker 与 MqttBrokerHost 启停边界

`BrokerWorker` 初次启动 Broker 失败时调用 `IHostApplicationLifetime.StopApplication()`，避免后台服务异常被 Host 配置忽略后进程假存活；连续重启失败超过 `maxConsecutiveFailures`（默认 10）同样请求停止。停机时先调用 `base.StopAsync` 取消监控循环，再停止 Broker，避免停机期间监控循环看到 `IsRunning=false` 后触发重启。

`MqttBrokerHost.StartAsync` / `StopAsync` 共用 `_lifecycleLock` 生命周期锁，避免并发启动创建两个 Server 实例。`StartAsync` 在进程内重启（BrokerWorker 监控自动重启）时先 `Dispose` 旧 Server 实例，避免句柄与内存泄漏，并在每次启动后重新放开 `_acceptingClientPublishes`。`StopAsync` 先设置 `_acceptingClientPublishes = false` 并调用 `_mqttServer.StopAsync()`，之后才解绑 7 个事件处理器：反序解绑会在通知窗口内让客户端发布落入 Broker 默认分发路径。QoS 越界时回退到 `Mqtt:DefaultQos`。

### 5.8 统一 Kestrel 单端口与自适应静态托管设计

- **统一 Kestrel 单端口监听**：在主服务注册拦截装饰器收集指标后，通过单个 Web 端口同时对外提供轻量级 API 端点与静态大屏，避免 5000 / 5001 重复暴露同一套站点。
- **自适应物理路径回退**：Dashboard 支持物理静态网页托管（自适应 `AppContext.BaseDirectory/wwwroot` 与开发期 `ContentRootPath/wwwroot`），本地 `dotnet run` 与 Windows 服务生产运行部署使用同一套逻辑。
- **无代理直连**：大屏直接通过相对路径 `/api/` 访问主服务的指标和审计日志接口，无需 HttpClient 代理，不存在跨域 (CORS) 限制与代理损耗。
- **Web 开关真实关闭 HTTP 宿主**：入口先从 `AppContext.BaseDirectory` 读取 `Web:Enabled`；为 `false` 时走 `Host.CreateApplicationBuilder`（普通 Worker Host），不创建 `WebApplication`，因此不会启动 Kestrel 监听；为 `true`（默认）时走 `WebApplication.CreateBuilder` 并在 `webOptions.Port` 上 `ListenAnyIP`。
- **页面不内嵌 API Key**：`/` 与 `/index.html` 不再注入 `Web:ApiKey`，改由运维在页面录入并保存到浏览器 `sessionStorage`，响应统一加 `Cache-Control: no-store`。
- **API Key 常量时间比较**：`Program.IsApiKeyMatch` 用 `CryptographicOperations.FixedTimeEquals` 比较 `X-Api-Key` 的 UTF-8 字节，长度不同直接判定不匹配；匹配语义仍是区分大小写的完全相等。
- **筛选日期按本机时区解释**：`Program.TryParseFilterDate` 使用 `DateTimeStyles.AssumeLocal` 并把 UTC 结果换算为本机时间，与审计表用 `DateTime.Now` 写入的 `CreatedAt` / `UpdatedAt` 列对齐；解析失败由调用方返回 400。
- **审计最终态快照**：消息审计库使用 `message_audit` 单表保存每条消息的最新态/最终态，不保存状态流水。`MetricsService` 在后台写库前按 `MessageId` 合并短时间内的 Queued 与终态，`AuditRepository` 继续使用 SqlSugar ORM 批量 Upsert，保持后续服务器数据库迁移兼容性。
- **Serilog 静态门面接线**：`Program.ConfigureLoggingAndServices` 同时执行 `AddSerilog(logger)` 与 `Log.Logger = logger`；只调用前者不会设置静态门面，`Main` 的 `Log.Fatal` / `Log.CloseAndFlush` 会退化为静默空操作。
- **配置集中校验**：`ReliabilityOptions` 用 `AddOptions().Validate(...).ValidateOnStart()` 集中校验（`QueueCapacity >= 1`、`MaxConcurrentHandlers >= 0`、`MaxPendingRetryTasks >= 0`、各超时与重试延迟为正、`RetryMaxDelayMs >= RetryBaseDelayMs`、`DeliverySemantics` 只支持 `AtLeastOnce`），`MqttOptions` 校验 `TcpPort` 在 1-65535；误配在启动时失败，而不是运行期隐式退化。`Program.ValidateAuthConfiguration` 校验认证配置一致性：`Auth:AllowAnonymous=true` 且配置了账号时记录 Warning，`Auth:AllowAnonymous=false` 且没有账号时抛 `InvalidOperationException`。
- **审计初始化降级**：Web 面审计仓储初始化失败只记录 Error 并降级为"审计不可用"，不拖停 MQTT 转发主链路；启动日志输出 Web 端口与 API 认证状态。
- **载荷缓存统一有界**：`MetricsService.SetBoundedPayload` 是唯一的载荷写入方法（空载荷写 `[空载荷]`、死信回填写非法 Base64 提示），上限 `MaxPayloadCount = 100`；只有键首次进入缓存时才登记驱逐键，同一 `MessageId` 在 Received / Forwarded / DeadLetter 阶段的重复写入不会挤占驱逐队列、提前淘汰仍然有效的载荷。
- **重试计数语义**：`TotalRetries` 按"带重试的转发尝试"计数 1（传入的 `retryCount` 是累计值，直接累加会与审计表 `RetryCount` 列对不上）。
- **拒绝终态审计**：`MetricsMessageQueue.EnqueueAsync` 入队失败时调用 `IMetricsService.RecordRejectedMessage`，以 `Status="Rejected"` 写入终态审计，避免被丢弃消息在审计表里永久停留在 `Queued`。
- **审计存储卡片按真实配置渲染**：`GET /api/settings/audit-storage`（`Program.BuildAuditStorageSettings`）把 `AuditStorage` 的提供程序、SQLite `Data Source`、保留天数、清理调度、VACUUM 开关与两个归档提示阈值下发到页面；响应刻意不含连接串原文，非 SQLite 提供程序只回提供程序名，因为未配置 `Web:ApiKey` 时页面匿名可访问。页面不再写死任何审计配置，卡片底部静态说明「保留策略只有按天数清理、归档提示阈值不删除数据」。

### 5.9 停机顺序（注册顺序即停机逆序）

`Program.RegisterHostedServices` 的真实注册顺序是 `QueueMetricsWorker → BrokerWorker → DeliveryWorker → AuditCleanupWorker`（`AuditCleanupWorker` 仅在 `enableWeb=true` 时注册）。Host 按注册逆序停止，因此实际停机顺序是 **AuditCleanupWorker 最先停 → DeliveryWorker → BrokerWorker → QueueMetricsWorker 最后停**。

这样排序的原因：排空阶段必须让 Broker 保持运行，才能继续把队列剩余消息注入给订阅者；`QueueMetricsWorker` 最后停止，停机排空期间仍可观察队列长度与峰值。审计清理任务不参与停机排空，注册在最后（最先停止）可缩短停机时间。`HostShutdownOrderTests.RegisterHostedServices_RegistersShutdownSafeOrder` 断言该注册顺序与停机不变式，`RegisterHostedServices_WebDisabled_ShouldNotRegisterAuditCleanupWorker` 断言 Web 关闭分支不注册清理任务。

### 5.10 停机封堵语义

停机时先"封堵"再"排空"，Broker 不停：

- `IMqttBrokerHost.StopAcceptingClientPublishes()` 是 `MessageDeliveryService.StopAsync` 的第一步，调用 `MqttBrokerHost.StopAcceptingClientPublishes()` 把 `_acceptingClientPublishes` 置为 `false`
- `OnInterceptingPublishAsync` 检查该标志：为 `false` 时设置 `ProcessPublish = false` 并记录 Warning，客户端新发布既不进入内部队列也不走 Broker 默认分发
- Broker 本身继续运行，`IMqttBrokerHost.PublishAsync` 仍可注入，排空阶段队列剩余消息照常投递
- Broker 的停止发生在 `BrokerWorker.StopAsync`（即排空结束之后），此时 `MqttBrokerHost.StopAsync` 才真正停止 Server 并解绑事件处理器

### 5.11 审计持久化与后台 writer 边界

- `MetricsService` 持有消息审计（`ConcurrentDictionary`，上限 `MaxPendingAudits = 50000`）与客户端历史（`ConcurrentQueue`，上限 `MaxPendingClientHistories = 10000`）两个有界待写队列，由同一个后台 writer 批量刷盘；审计批大小 1000，客户端历史批大小 200
- MQTT 事件回调只做有界入队并唤醒 writer，绝不在回调线程上访问数据库；`MetricsClientRegistry` 的 `RecordHistory` 捕获全部异常，历史记录失败不影响连接、断开、订阅主链路
- 审计批次写入失败时回填待写队列，回填同样受 `MaxPendingAudits` 上限约束，达到上限后丢弃并记录一次 Error；退避按 1s → 2s → 4s → 8s → 16s → 30s 递增；客户端历史写入失败只记录日志，不回填、不退避，避免拖慢消息审计追平速度
- 正常入队路径与失败回填路径共用同一个 `_pendingAuditOverflowLogged` 去重标志：同一故障窗口内"队列已达上限"只告警一次，队列真正排空后由 `FlushPendingAuditsAsync` 复位
- `MetricsService.Dispose` 用 `AuditWriterShutdownWaitMs = 5000` 限时等待审计 writer 完成最后一轮刷盘：超时记录 Warning 并继续释放资源，且不释放 writer 仍在使用的 `_pendingAuditSignal` / `_auditWriterCts`
- 同优先级状态合并按 `UpdatedAt` 取新；状态优先级为 Rejected / DeadLetter (5) > Failed / Succeeded (4) > Forwarding (3) > Routing (2) > Queued (1)
- `AuditRepository` 分页参数在仓储层统一收敛（页长上限 200，页码上限 1000000），`InitializeAsync` 收敛上次非正常关闭残留的在途状态为 `Failed`，并按 `MessageArchiveThreshold` / `ClientHistoryArchiveThreshold` 打印迁移阈值提示，不触发额外删除
- `GET /api/settings/audit-storage` 是审计配置的只读展示入口：`Program.BuildAuditStorageSettings` 只下发 `Provider`、SQLite `Data Source`、`RetentionDays`、`CleanupEnabled`（`RetentionDays > 0`）、`CleanupAtHour`、`CleanupIntervalMinutes`、`VacuumAfterCleanup` 与两个归档提示阈值，不包含连接串原文，非 SQLite 提供程序只回提供程序名。Dashboard 的「审计持久化存储」卡片完全由该端点驱动，页面里不存在写死的保留上限或物理清理频率
- 审计数据保留清理由 `AuditCleanupWorker` 负责：`AuditStorage:RetentionDays` 默认 30 天（`0` 表示关闭清理），启动立即清理一次，之后每天至少一次（`CleanupAtHour` 默认 3 点；留空时按 `CleanupIntervalMinutes` 等间隔，启动校验范围 1-1440 分钟）。截止时间取「`DateTime.Now` − 保留天数」，与审计写入的本地时间基准一致
- 清理分批执行：先按 `CreatedAt` / `Timestamp` 升序取一批主键（SQLite 500 条、其他提供程序 2000 条），再按主键分块删除（单条 SQL 的 IN 参数上限 900，对应 SQLite 默认 `SQLITE_MAX_VARIABLE_NUMBER = 999`）；不使用 `Deleteable().Take(n)`，因为 SQLite 的 `DELETE ... LIMIT` 依赖编译选项 `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`。每批还以「本批是否真的删掉行」作为退出条件，避免并发写入导致同一批主键被反复选中
- 删除在 `_writeLock` 内与审计写入互斥；`VACUUM` 刻意在 `_writeLock` 之外执行：大库 `VACUUM` 耗时可观，持锁会把审计写入队列堵到内存上限，代价高于让 `VACUUM` 偶发遇到 SQLite 忙锁后在下一轮重试（失败只记 Warning）。`VACUUM` 只在 `DbType.Sqlite` 上执行
- 两张表的清理互相隔离：单张表持续失败（例如单表长时间被锁）只记 Error，另一张表仍然清理，避免一张表的故障让另一张表无界增长
- Dashboard 汇总带 `DashboardSummaryCacheTtlMs = 5000` 缓存，避免前端按秒轮询把无索引聚合查询打成扫描风暴；累计计数来自启动基线 + 运行期增量，清理不会使其回落
- `EnableDeadLetter=false` 时 `DeadLetterService.WriteAsync` 用 Error 级别记录"死信功能已禁用，消息将被直接丢弃"
