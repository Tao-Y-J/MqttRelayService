# 仓库上下文管理入口

本文档是每次会话开始时的必读入口，用于快速恢复上下文。

## 1. 项目基本信息

- **项目名称**：MqttRelayService
- **技术栈**：.NET 8 + `Microsoft.NET.Sdk.Web`（Worker Service 宿主，`Web:Enabled=true` 时用 Kestrel 承载 Web 管理面与静态资源）+ MQTTnet 5.x + Serilog + SqlSugarCore（审计持久化，默认 SQLite）
- **部署形态**：Windows Service（win-x64）
- **核心定位**：轻量级 MQTT Broker + 内部消息转发 + 单端口 Web 管理面

## 3. 关键决策与约束（长期有效）

### 3.1 文本文件编码规范（不可变更）

仓库中文文本长期运行在 Windows / PowerShell 环境下，编码规则已踩坑确认：

| 范围 | 编码 | 原因 |
|----------|------|------|
| 默认文本文件（`.md`、`.ps1`、`.json`、`.yml`、`.xml`、`.cs` 等） | **UTF-8 with BOM** | 中文内容在 Windows / PowerShell 5.1 下读取更稳定，无 BOM 时容易按系统编码（GBK）解码并出现乱码 |
| `.cmd` / `.bat` | **GBK(936)** | cmd 默认用 GBK 解码，UTF-8 会导致中文乱码或命令解析异常 |

> 新增或修改文本文件时，除仓库内已有明确例外外，默认写回 `UTF-8 with BOM`。修改 `.cmd` / `.bat` 时必须保持 `GBK(936)`。

### 3.2 MQTTnet 5.x API 适配要点

- `MqttServerFactory.CreateMqttServer()` 返回 `MqttServer`（不是 `IMqttServer`）
- 事件全面异步化：`ValidatingConnectionAsync`、`InterceptingPublishAsync`、`ClientConnectedAsync` 等
- `Payload` 属性是 `ReadOnlySequence<byte>`，需用 `System.Buffers.BuffersExtensions.ToArray()` 转换
- `ClientDisconnectedEventArgs` 没有 `Reason` 属性，使用 `DisconnectType`

### 3.3 可靠性设计原则

- 所有后台入口必须顶层 `try/catch`
- MQTT 事件回调只做轻量操作（入队即返回）
- 默认"至少一次"转发语义，允许重复
- 消息唯一标识 `MessageId`（GUID）
- 有界队列（`System.Threading.Channels`），禁止无界增长
- 超过最大重试次数进入死信文件（JSON 格式）

### 3.4 C# 命名空间风格

- 全仓库 `.cs` 文件统一使用块级命名空间写法：`namespace MqttRelayService.Utilities { ... }`
- 不使用文件作用域命名空间写法：`namespace MqttRelayService.Utilities;`
- 新增或修改 C# 文件时，必须保持块级命名空间风格

### 3.5 配置文件注释约定

- `appsettings.json` / `appsettings.Development.json` 全量携带中文 `//` 注释，注释写「作用 + 单位 + 取值/默认值 + 边界」，不逐字复述键名；新增或修改配置项时必须同步补注释，否则运维无法判断该键用途。
- 配置文件允许 `//` 行注释与 `/* */` 块注释，**不允许尾随逗号**：`Scripts/install-service.ps1` 与 `uninstall-service.ps1` 用 Windows PowerShell 5.1 的 `ConvertFrom-Json` 读取 `Service.Name`、`Mqtt.TcpPort`、`Web.Port`，该解析器既不支持注释也不支持尾随逗号，脚本通过 `Read-RelayJsonConfig` 先剥离注释再解析。
- 不要在脚本里绕开 `Read-RelayJsonConfig` 直接 `Get-Content $configPath -Raw | ConvertFrom-Json`：解析失败只会退化成一条 Warning 加默认服务名，不会让安装失败。
- `ConfigurationFileCompatibilityTests` 断言上述契约（注释存在、剥离注释后是严格 JSON、各配置节能绑定并通过启动校验、脚本走注释容忍读取），改配置或改脚本后必须让该测试通过。

## 4. 当前版本边界

已实现的子系统：

- **MQTT Broker + 转发主链路**：内存有界队列（`InMemoryMessageQueue`）、重试（运行期非阻塞后台调度 + 停机同步退避）、死信（本地 JSON 文件 + 按天目录）、优雅停机排空、队列指标（`QueueMetricsWorker` 写 `data/metrics/queue-metrics.json`）、Windows Service 安装/卸载脚本。
- **审计数据清理**：`AuditCleanupWorker`（Web 管理面开启时才注册）按 `AuditStorage:RetentionDays`（默认 30 天）删除超期消息审计与客户端历史，启动立即清理一次，之后每天至少一次，清理后在写锁之外执行 SQLite `VACUUM` 回收文件空间。
- **Web 管理面**：`Web:Enabled` 默认 `true`，`Web:Port` 默认 `5000`，同一个 Kestrel 实例同时提供 Dashboard 页面（`/`、`/index.html`）与 `/api/*`；`/api` 通过 `X-Api-Key` 请求头校验 `Web:ApiKey`，密钥为空时全部放行，`/api/health` 始终匿名可访问。
- **审计持久化**：`AuditRepository`（SqlSugar ORM，`AuditStorage:Provider` 默认 `Sqlite`，数据文件默认 `data/audit.db`）保存消息审计与客户端连接/订阅历史；后台批量 Upsert，待写队列有界（消息审计 50000 条、客户端历史 10000 条）。审计数据由 `AuditCleanupWorker` 按保留天数清理：`AuditStorage:RetentionDays` 默认 30 天、`0` 表示关闭清理，启动立即清理一次，之后每天至少一次（`AuditStorage:CleanupAtHour` 默认 3 点，留空则按不超过 1440 分钟的间隔），清理后按 `AuditStorage:VacuumAfterCleanup` 回收 SQLite 文件空间。
- **吞吐调控**：`ThroughputController` 支持在线调整每秒转发量与并发度，并发度受 `Reliability:MaxConcurrencyHardLimit`（默认 200）约束。

未实现的边界：

- 磁盘队列与消息持久化（README 和需求文档已明确声明可靠性边界）
- ACL、用户/角色体系、TLS：Web 管理面的安全边界完全依赖网络可达性与 `Web:ApiKey`；MQTT 监听与 Web 管理面都只有明文 TCP/HTTP
- `EchoToSender=false` 只对 MQTT 5.0 订阅者生效（出站拦截依赖 MQTT 5.0 User Properties，MQTT 3.1.1 没有该字段）
