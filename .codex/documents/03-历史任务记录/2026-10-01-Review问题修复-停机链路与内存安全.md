# Review 问题修复：停机链路、内存上限、审计口径与 Web 安全

## 1. 背景

本任务基于一次全仓库静态 Review（结论：1 项严重、约 20 项高/中、若干低级别问题）实施修复。
Review 确认的核心事实是：**停机排空链路实际无法投递任何消息**，且存在内存无界增长、MQTT 事件回调内直接写库、入队失败留下永久 `Queued` 审计行、并发槽位永久泄漏、Web 页面内嵌 API Key 与存储型 XSS 等问题。

本记录只描述本次实际落地的修改。

## 2. 实际修改

### 2.1 停机链路（核心修复）

- 停机顺序反转：`Program.RegisterHostedServices` 注册顺序改为 `QueueMetricsWorker → BrokerWorker → DeliveryWorker`。
  Host 逆序停止后，**DeliveryWorker 最先停止**（封堵入口 → 取消消费者 → 多轮排空），**BrokerWorker 随后停止**，`QueueMetricsWorker` 最后停止。
  原因：原顺序先停 Broker，导致排空阶段 `IMqttBrokerHost.PublishAsync` 因 `MqttServer.IsStarted == false` 直接返回 false，队列中每条剩余消息只能烧退避并被写成死信，超出排空预算的消息回队后随进程退出丢失。
- `IMqttBrokerHost` 新增 `StopAcceptingClientPublishes()`：`MqttBrokerHost` 内新增 `_acceptingClientPublishes` 标志，`OnInterceptingPublishAsync` 在停机期阻断客户端新发布（`ProcessPublish = false` + Warning 日志），Broker 本身保持运行；
  `MetricsMqttBrokerHost` 透传该方法；`MessageDeliveryService.StopAsync` 在阶段 0 调用它。
- `MessageDeliveryService.StopAsync` 的排空改为多轮收敛：`DrainQueueRoundAsync` 返回本轮排空数量/死信数量/是否读到空队列，`SnapshotConsumerTasks` 判断是否仍有消费者可能把在途消息保留回队列；
  当「队列空且消费者全部退出」时才算排空完成，否则用剩余排空预算等待消费者结束后再次 drain，直到排空超时。
  停止日志改为区分「已排空 N 条（其中 M 条转入死信）」与剩余数量。

### 2.2 队列、死信与重试

- `InMemoryMessageQueue.EnqueueAsync`：区分「调用方取消」（向上抛 `OperationCanceledException`）与「入队超时」（返回 false）。停机路径新增 `TryEnqueueOnShutdownAsync` 封装，把强制超时统一视为本次入队失败，由调用方决定回队或转死信。
- `DeadLetterService`：
  - 写盘改为「临时文件 + `File.Move(overwrite: true)`」原子落盘，写盘使用独立的强制超时，不再继承调用方截止 token（原实现会在停机途中截断死信 JSON 且消息已出队）。
  - 新增 `Reliability:DeadLetterRetentionDays`（默认 30，0 或负数不清理），每天最多扫描一次并删除超过保留天数的日期目录。
  - `EnableDeadLetter = false` 时的日志级别从 Warning 提升为 Error，明确「消息被直接丢弃」。
- `MessageDeliveryService` 的停机/恢复路径统一使用 `CreateShutdownForceTimeoutSource()`（`using` 释放，修复原实现每次调用泄漏一个 `CancellationTokenSource` 定时器）；`MoveToDeadLetterAsync` 内部退避等待改受生命周期 token 约束，不再用 `CancellationToken.None` 睡满最大退避。
- 死信记录补齐「目标 ClientId 或目标规则」：新增 `ForwardMessage.RouteTargetSummary`，由 `BuildTargetSummary` 生成命中订阅者摘要，写入 `DeadLetterRecord.TargetClientId`。

### 2.3 指标与审计

- `MetricsService.CachePayload` 统一走新增的 `SetBoundedPayload`：空载荷分支、死信 Base64 异常分支都登记驱逐键，载荷缓存（上限 100 条）不再因空载荷消息无界增长。
- `TotalRetries` 改为「每次带重试的转发尝试计 1」，不再累加累计重试次数（原实现把重试 3 次的消息计成 1+2+3=6）。
- 审计合并 `Failed`/`Succeeded` 同优先级状态时改为按 `UpdatedAt` 取新，避免失败批次回填用旧记录覆盖新终态。
- 审计待写队列的**失败回填路径同样受 `MaxPendingAudits`（50000）上限约束**，达到上限丢弃本次回填并记录一次 Error；原实现注释明确写「不受上限约束」，在审计库长时间不可用时无界增长。
- 新增客户端历史待写队列（`MaxPendingClientHistories = 10000`，`RecordClientHistory`），与消息审计共用后台 writer 批量落库；新增 `IAuditRepository.RecordClientConnectionHistoriesAsync` 批量写入。
- 新增 `RecordRejectedMessage`：入队失败时写入 `Status = "Rejected"` 终态审计（`MetricsMessageQueue` 在 `EnqueueAsync` 返回 false 时调用），消除审计表永久残留 `Queued` 行导致 Dashboard 待处理数虚高的问题；`Rejected` 在状态优先级中与 `DeadLetter` 同级（5），不会被迟到的 `Queued` 覆盖。
- Dashboard 汇总查询新增 5 秒缓存（`DashboardSummaryCacheTtlMs`）：前端按秒轮询，而汇总需要在审计表上做多次无索引聚合，原先每次轮询都会全表统计。
- `MessageAuditRecord` 新增 `Status` 与 `UpdatedAt` 索引组。

### 2.4 MQTT 协议与生命周期

- `MqttBrokerHost.PublishAsync`：**所有服务端注入（即使没有 sourceClientId）都会附加 `x-relay-message-id`**，使发布拦截器能稳定区分「服务端注入」与「客户端原始发布」；QoS 越界时回退 `Mqtt:DefaultQos`（该配置项此前绑定后从未被读取）。
- `OnInterceptingPublishAsync` 新增两道守卫：无来源标识（`ClientId` 为空）的发布直接阻断默认分发并丢弃，避免以空 ClientId 记账与丢失 `SourceClientId`；停机期阻断新发布。
- `MqttBrokerHost.StartAsync/StopAsync` 增加生命周期锁与旧实例释放；停 Broker 改为**先 `StopAsync` 再解绑事件处理器**（原顺序会在通知窗口内让客户端发布落入 Broker 默认分发，绕过队列、审计、重试、死信与 EchoToSender，且断开事件不再注销会话）。
- `ClientRegistry.UnregisterAsync`：`connectionId` 为空时不再删除会话（只记 Warning），修复「无连接标识的延迟断开误删新连接」；`UpdateActivityAsync` 增加空标识守卫与顶层 try/catch。
- `MessageRouter.TopicMatches`：补 MQTT `$` 前缀规则（`#`/`+` 开头的过滤器不匹配 `$` 主题），`#` 只在过滤器末级才匹配。

### 2.5 MQTT 事件回调轻量化

- `MetricsClientRegistry` 不再在 CONNECT/DISCONNECT/SUBSCRIBE 回调里 `await` SqlSugar 写库（原实现违反需求文档「禁止在 MQTT 消息回调里直接做数据库访问」并争用全局写锁），改为调用 `IMetricsService.RecordClientHistory` 有界入队；断开事件在后仍在线且 ConnectionId 不同时记为 `DisconnectedStale`，不再把旧连接的延迟断开写成新连接的断开。

### 2.6 Web 面安全与参数收敛

- `Program.MapDashboard` 不再注入 `window.__dashboardAuth`，`BuildDashboardHtml` 已删除：原实现把 `Web:ApiKey` 明文内嵌到无需鉴权的 `/` 与 `/index.html`，使 `X-Api-Key` 认证完全失效。页面响应新增 `Cache-Control: no-store`。
- `wwwroot/index.html`：
  - `dashboardFetch` 改为从 `sessionStorage` 读取密钥，收到 401 时弹窗让运维录入并重试；不再依赖服务端注入。
  - 在线客户端表与死信表对 `clientId`/`username`/订阅主题/`topic`/`errorMessage` 全部经 `escapeHtml`（原实现未转义即拼入 `innerHTML`，构成存储型 XSS；同文件其它表已正确转义）。
  - 内联 `onclick` 中的消息 ID 改为 `encodeURIComponent` 传递并在 `openMessageDetail` 内解码；`getStatusChinese` 对未知状态转义并识别 `Rejected`；新增 `.badge-rejected` 样式。
  - 修正命中提示读取不存在的 `log.matchedSubscriberCount`，改用实际存在的 `log.isSubscriberHit`。
- 分页与筛选参数在 API 层（`NormalizePage`/`NormalizePageSize`）与仓储层（`NormalizePaging`，页长上限 200、页码上限 1000000）双层收敛；`startDate`/`endDate` 解析失败返回 400，并校验 `start <= end`。

### 2.7 启动、配置与可观测性

- `Program.ConfigureLoggingAndServices` 增加 `Log.Logger = logger`：原实现只用 `logging.AddSerilog(logger)`，未设置 Serilog 静态门面，导致 `Log.Fatal(ex, "应用程序启动失败")` 与 `Log.CloseAndFlush()` 都是空操作，启动致命错误在 Windows 服务下完全无输出。
- Web 面审计初始化失败降级为 Error 日志并继续运行，不再把整个 MQTT 转发主链路一起拖停；启动日志输出 Web 端口与 API 认证状态，`Web:ApiKey` 为空时额外 Warning。
- 新增 `ValidateAuthConfiguration`：`Auth:AllowAnonymous=false` 且没有任何账号时启动失败；匿名开启时对「Users 与 ClientIdPrefix 全部不生效」明确告警。
- `ReliabilityOptions` 使用 `AddOptions<ReliabilityOptions>().Validate(...).ValidateOnStart()` 集中校验（队列容量、各类超时、退避上下界、`DeliverySemantics` 只支持 `AtLeastOnce`）；`MqttOptions` 校验端口范围。
- `AuditRepository.InitializeAsync` 增加按 `MessageArchiveThreshold`/`ClientHistoryArchiveThreshold` 的启动迁移阈值提示（不自动删除数据）。
- `DeliveryWorker` 注入 `IHostApplicationLifetime` 并增加顶层 try/catch，启动失败时记录 Error 并 `StopApplication()`；原实现无兜底，配合 `BackgroundServiceExceptionBehavior.Ignore` 会形成「Broker 继续收消息、消费者已死」的假存活。
- `Program.RunWebHostAsync` 的 `MapWebEndpoints` 之前新增装饰器 logger 注入（`MetricsMqttBrokerHost`/`MetricsDeadLetterService`），装饰器内的指标调用全部 try/catch，指标失败不再影响被装饰对象的投递结果。

### 2.8 依赖注入循环依赖修复（Web 管理面启动卡死，本次实际启动服务时发现）

- 现象：以 `Web:Enabled=true`（默认配置）启动时，进程在输出「审计持久化初始化成功」「消息队列已初始化」之后**永久卡死**：不绑定 1883/5000，不打印任何异常，进程既不退出也不消耗 CPU。
- 根因：装饰器与被装饰依赖之间存在构造期循环依赖，且装饰器使用工厂委托注册，容器无法静态识别该环：
  - `MetricsService` 依赖 `IMessageQueue`，而 `IMessageQueue` 由 `MetricsMessageQueue` 装饰，其构造函数又需要 `IMetricsService`；
  - `MetricsService` 依赖 `IClientRegistry`，而 `IClientRegistry` 由 `MetricsClientRegistry` 装饰，本次改动让它也需要 `IMetricsService`（原先它只依赖 `IAuditRepository`，所以这一段是本次新引入的）。
- 证据：仓库内 `src/MqttRelayService/bin/Debug/net8.0/win-x64/Logs/relay-2026061821.log`（2026-06-18 两次启动记录）在同样的位置截断，说明该卡死**早于本次改动就已存在**；本次静态 Review 未发现该问题，是在真实启动服务 + 新增依赖注入解析测试后才定位。
- 修复：新增 `Utilities/LazyService<T>`（唯一公开构造函数为 `LazyService(IServiceProvider)`，并以静态 `From(T)` 提供测试用固定实例构造），`Program.ConfigureCoreServices` 注册开放泛型 `AddSingleton(typeof(LazyService<>))`；
  `MetricsMessageQueue` 与 `MetricsClientRegistry` 改为依赖 `LazyService<IMetricsService>`，在首次真正记录指标时才解析指标服务（此时容器已完成启动、单例已缓存，二者是同一个实例）。
  同时保留直接注入 `IMetricsService` 的构造重载，供单元测试使用。
- 边界：延迟解析只允许出现在装饰器构造期保存、业务调用期读取这一种用法；不得在构造函数中读取 `Value`，否则环会重现。

### 2.9 死代码与无效配置清理

- `ThroughputController` 删除 `Pause()`/`Resume()`/`IsPaused` 与暂停分支（暂停能力此前已从 API 移除，属不可达代码）；`WaitAsync` 在限速等待被取消时回滚已占用的并发槽位（原实现会永久泄漏槽位，默认并发为 1 时一次泄漏即永久堵死投递）。
- `MessagePayloadFormatter.Format` 删除（无调用方），保留 `ToBase64`。

## 3. 边界条件（本次明确不做的事）

- 不实现磁盘队列、消息持久化、集群、桥接与完整 ACL/TLS；README 与需求文档继续声明这些边界。
- 不改变「至少一次」投递语义与 `MessageId` 生成方式。
- 不改变审计表结构（仅在模型上增加索引声明），不实现历史数据自动删除，仅做阈值提示。

- 未对 `$` 开头主题的客户端发布做拒绝：该行为属于 ACL 策略，当前版本不支持 ACL。

## 6. 风险与后续建议

- **教训**：静态 Review 无法发现「工厂委托形式的循环依赖」这类只在真实容器解析时才暴露的缺陷；本次是靠实际启动服务与新增 `ServiceRegistrationTests`/`HostLifecycleTests` 才发现的。后续改动 DI 注册后必须跑这两个测试。
- 排空阶段的消费者等待会占用排空预算：若消费者长时间不响应取消，停机耗时将接近 `ShutdownDrainTimeoutMs`（已由 `HostOptions.ShutdownTimeout = ShutdownDrainTimeoutMs + 5000` 兜住）。
- Dashboard 汇总缓存为进程内 5 秒：多实例部署时各实例计数独立，当前版本定位为单机服务。
- 后续若需要真正的 Web 安全边界，应引入用户/角色与 TLS，而不是仅依赖 `Web:ApiKey` 与网络隔离。

对上一轮修复（已提交为 `5f4711c`）做了一次独立评审，逐条在代码中核对后确认 9 项遗留问题**全部属实**，本轮全部修复。

### 7.1 审计队列超限告警去重（原评审第 1 项）

- 问题：`MetricsService.EnqueueMessageAudit` 在待写队列达到 `MaxPendingAudits` 时对**每条**新消息打一条 Warning；审计库长时间故障叠加高吞吐时形成日志风暴。失败批次回填路径 `RequeueFailedAuditRecord` 此前已用 `_pendingAuditOverflowLogged` 去重，两条路径行为不一致。
- 修改：正常入队路径复用同一个 `_pendingAuditOverflowLogged` 标志，同一故障窗口只提示一次；队列真正排空后仍由 `FlushPendingAuditsAsync` 复位该标志。

### 7.2 Dispose 等待审计 writer 必须限时（原评审第 2 项）

- 问题：`MetricsService.Dispose` 用 `_auditWriterTask.GetAwaiter().GetResult()` 无界同步等待，而 writer 退出前还要执行最后一轮 `FlushPendingAuditsAsync`。`Dispose` 由 DI 容器在 `HostOptions.ShutdownTimeout` 之外调用，审计库无响应时进程退出被无限阻塞。
- 修改：新增 `AuditWriterShutdownWaitMs = 5000`，改为 `Task.Wait(5000)` 限时等待；超时后记录 Warning 并继续释放资源，且此时**不**释放 `_pendingAuditSignal` 与 `_auditWriterCts`，避免仍在运行的 writer 撞上 `ObjectDisposedException`。`_dashboardSummaryLock` 在两条路径下都释放。

### 7.3 排空超时不得静默丢失在途消息（原评审第 3 项）

- 问题：`DrainQueueRoundAsync` 中消息已出队、`ProcessMessageAsync` 被排空预算取消时，原实现直接返回。该消息既回不到队列（`_queue.Count` 不含它），也不写死信，停机日志的"剩余 N 条"同样不含它。
- 修改：该分支先调用 `PreserveInFlightMessageAsync(message)`（重新入队，失败转死信）再结束本轮排空，与消费循环取消路径 `ConsumeLoopAsync` 的处理保持一致，并记录携带 `MessageId` 的 Warning。

### 7.4 并发等待去掉轮询（原评审第 4 项）

- 问题：`ThroughputController.WaitAsync` 捕获了 `_concurrencyTcs.Task` 却从未等待，实际靠 `Task.Delay(10)` 轮询；`Release()` / `UpdateMaxConcurrency()` 里的唤醒代码形同虚设。
- 修改：改为 `await concurrencyTask.WaitAsync(cancellationToken)`。该 TCS 的全部替换点（构造函数、`UpdateMaxConcurrency`、限速取消回滚、`Release`）都会对旧实例调用 `TrySetResult()`，因此不会挂死；取消直接在等待处抛出，此时未占用槽位，无需回滚。

### 7.5 API Key 比较改为常量时间（原评审第 5 项）

- 问题：`/api` 鉴权过滤器用 `string.Equals(..., StringComparison.Ordinal)` 比较密钥，存在按响应时间逐字节推测密钥的侧信道。
- 修改：新增 `Program.IsApiKeyMatch`，用 `CryptographicOperations.FixedTimeEquals` 比较 UTF-8 字节，长度不同直接判定不匹配。匹配语义（区分大小写、完全相等）不变。

### 7.6 载荷缓存驱逐键去重（原评审第 6 项）

- 问题：`SetBoundedPayload` 对同一 `MessageId` 的每次写入都登记一个驱逐键。同一消息会在 Received / Forwarded / DeadLetter 阶段被反复写入，重复键挤占驱逐队列，把仍在缓存中的载荷提前淘汰：写入 150 次同一热键后再写 99 个新键，旧实现缓存只剩 99 条且热键已被驱逐。
- 修改：仅在键首次进入 `_payloads` 时登记驱逐键。

### 7.7 Dashboard 方法体缩进（原评审第 7 项）

- `MetricsService.GetDashboardDataAsync` 的方法体比所在 `try` 块少一级缩进（编译无影响），本次统一补齐；`try` 的闭合括号与 `catch` 保持原有层级。

### 7.8 装饰器指标失败不再静默（原评审第 8 项）

- 问题：`MetricsMessageQueue.SafeRecord` 用 `Debug.WriteLine` 输出失败，Release 构建下指标记录异常完全不可见，与 `MetricsMqttBrokerHost` / `MetricsDeadLetterService` 的可选 logger 写法不一致。
- 修改：构造函数新增可选参数 `ILogger<MetricsMessageQueue>?`，失败改为 `LogError`；`Program.ConfigureCoreServices` 传入真实 logger。

### 7.9 筛选日期时区语义（原评审第 9 项）

- 问题：`TryParseFilterDate` 使用 `DateTimeStyles.None`，时区语义未定义；审计表的 `CreatedAt` / `UpdatedAt` 由 `DateTime.Now` 写入，带 `Z` 的输入会与本机时间列比较出非预期区间。
- 修改：改为 `DateTimeStyles.AssumeLocal`，并对 UTC 结果显式 `ToLocalTime()`；方法改为 `internal` 以便测试，XML 注释写明"按服务器本机时区解释"。解析失败仍然返回 400。
