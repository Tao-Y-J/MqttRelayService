# 2026-10-01 审计存储面板改为读取真实配置

## 问题

Dashboard 的「审计持久化存储」卡片（`src/MqttRelayService/wwwroot/index.html`）是静态 HTML：数据库类型写死 `Configured Provider`，文件路径写死 `data/audit.db`，并展示 `自动滑动容量清理 / 已启用 (Enabled) / 消息表保留上限 20,000 条 / 客户端历史保留上限 5,000 条 / 物理清理频率 每 100 次写入检测`。

后端从未实现按行数上限的裁剪，也没有按写入次数触发的物理清理：`IAuditRepository` 只有 `DeleteExpiredMessageAuditsAsync` / `DeleteExpiredClientHistoriesAsync` 两个按时间截止的删除方法，`AuditCleanupWorker` 只用 `AuditStorage:RetentionDays` 计算 cutoff。运维看到该卡片会以为审计库存在 2 万条 / 5 千条行数上限，从而误判真实保留策略（真实生效的只有 30 天按天清理）。

## 实际实现

### 1. 仓储复用连接串解析（`Services/Implementations/AuditRepository.cs`）

- 新增 `internal static string? ExtractSqliteDataSource(string? connectionString)`：按 `;` 分段、按首个 `=` 拆分、大小写不敏感匹配 `Data Source`，返回连接串里原样写出的值，不做路径展开。
- `ResolveSqliteDataSourcePath` 改为先调用该方法，再按「根路径原样返回、相对路径基于 `AppContext.BaseDirectory` 展开」处理，行为与改动前一致。

### 2. 只读配置端点（`Program.cs`）

- 新增 `internal static AuditStorageSettingsDto BuildAuditStorageSettings(AuditStorageOptions options)` 与 `AuditStorageSettingsDto` record，字段为 `Provider`、`SqliteDataSource`、`AutoInitializeSchema`、`RetentionDays`、`CleanupEnabled`（`RetentionDays > 0`）、`CleanupAtHour`、`CleanupIntervalMinutes`、`VacuumAfterCleanup`、`MessageArchiveThreshold`、`ClientHistoryArchiveThreshold`。
- 新增 `GET /api/settings/audit-storage`，注册在 `api.MapGroup("/api")` 内，因此继承 `X-Api-Key` 端点过滤器；只在 `MapWebEndpoints` 中注册，Web 关闭时不暴露。
- 安全边界：响应不含连接串原文。只有 `ParseDbType(Provider)` 判定为 `Sqlite` 时才回传连接串里的 `Data Source`；其他提供程序 `SqliteDataSource` 为 `null`，只回传提供程序名。`IsSqliteProvider` 捕获 `ArgumentException`，非法的提供程序名不会让接口返回 500。
- 接入方式：端点直接注入 `IOptions<AuditStorageOptions>`；`MetricsService` 构造函数与 `/api/metrics` 载荷形状不变。

### 3. 前端卡片（`wwwroot/index.html`）

- 卡片动态值改为占位 `-` 加 id：`audit-provider`、`audit-storage-path`、`audit-retention-days`、`audit-cleanup-schedule`、`audit-vacuum`、`audit-message-threshold`、`audit-history-threshold`；「审计写入互斥锁」行保留静态文本 `SemaphoreSlim(1, 1)`，对应 `AuditRepository._writeLock`。
- 删除四行未实现能力的描述：`自动滑动容量清理`、`消息表保留上限`、`客户端历史保留上限`、`物理清理频率`。
- 卡片底部增加静态说明：保留策略只有按天数清理，不存在按行数上限的自动裁剪；归档提示阈值只在启动时写告警日志、不删除数据。
- 新增 `fetchAuditStorageSettings()` 与 `updateAuditStorageUI(settings)`：在 `DOMContentLoaded` 中拉取一次（审计配置在运行期没有改写端点），全部用 `textContent` 赋值；保留天数、清理调度（每日整点或等间隔）、VACUUM 开关、两个归档阈值都由响应填充，`cleanupEnabled` 为 false 时显示「已关闭（RetentionDays=0，数据无界增长，需运维手工维护）」。拉取失败只记录 console 错误并保留 `-`。

### 4. 测试

- `DashboardPageTests` 新增 `DashboardSource_ShouldRenderAuditStorageFromRealConfiguration`：断言页面源码不再包含上述五类静态假值，且卡片 id 与 `dashboardFetch('/api/settings/audit-storage')` 存在。
- 新增 `AuditStorageSettingsTests`：覆盖 Sqlite 取到 `Data Source`、`RetentionDays=0` 时 `CleanupEnabled=false`、每日整点与等间隔两种调度字段、非 Sqlite 响应序列化后不含 `User Id` / `Password` / 连接串原文、非法提供程序名不抛异常，以及 `ExtractSqliteDataSource` 的大小写不敏感匹配与「非 `Data Source` 连接串返回 null」。

## 边界

- 只读接口不提供运行期改写审计配置的入口。
- 面板不展示其他提供程序的连接串，也不把 SQLite 相对路径展开为绝对路径。
- 后端审计保留行为零变化：仍然只有 `RetentionDays` 按天删除；`MessageArchiveThreshold` / `ClientHistoryArchiveThreshold` 仍然只在启动时记录告警日志。
- 未实现按行数上限的裁剪：行数上限按最旧行先删、与记录年龄无关，会删掉未满 30 天的记录，与「保留 30 天」的承诺冲突；因此面板、README 与需求文档统一只描述按天清理。
