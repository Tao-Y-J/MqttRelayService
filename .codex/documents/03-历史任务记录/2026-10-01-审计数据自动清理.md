# 2026-10-01 审计数据自动清理（本地 SQLite 默认保留 30 天）

## 目标

为本地 SQLite 审计库加入数据保留清理，解决审计表与客户端历史表随运行时间无界增长的问题：默认只保留最近 30 天，保留天数可配置，且清理每天至少执行一次。

## 实际实现

### 配置（`AuditStorage` 节）

新增四个配置项，默认值写在 `AuditStorageOptions` 与 `appsettings.json` / `appsettings.Development.json`：

| 配置项 | 默认值 | 语义 |
|--------|--------|------|
| `RetentionDays` | `30` | 保留天数，`0` 表示关闭清理 |
| `CleanupAtHour` | `3` | 每日清理时刻（本机时间整点 0-23），留空表示按间隔执行 |
| `CleanupIntervalMinutes` | `1440` | `CleanupAtHour` 为空时的清理间隔，启动校验范围 `1-1440` |
| `VacuumAfterCleanup` | `true` | 清理后是否执行 SQLite `VACUUM` 回收文件空间 |

`Program.ValidateAuditStorageConfiguration` 在 `ConfigureCoreServices` 中做集中校验：`RetentionDays < 0`、`CleanupAtHour` 不在 `0-23`、`CleanupIntervalMinutes` 不在 `1-1440` 都在启动时抛 `InvalidOperationException`。把间隔上限收紧到 1440 分钟，是「每天至少清理一次」的机制保证：误配成 30 天间隔会在启动时失败，而不是运行期静默不清理。

### 清理调度（`Workers/AuditCleanupWorker.cs`）

`BackgroundService`，只在 Web 管理面开启（存在审计仓储）时由 `Program.RegisterHostedServices(services, enableWeb)` 注册。执行语义：

1. 启动立即清理一轮，收敛服务长时间停机期间堆积的超期数据。
2. 之后调用静态的 `ComputeNextRunAt(now, cleanupAtHour, intervalMinutes)` 计算下一轮：配置了整点时取「今天的该整点，已过则取明天」，未配置时取 `now + intervalMinutes`。这样每 24 小时至少覆盖一个整点，天然满足「每天至少一次」。
3. `ExecuteAsync` 顶层 `try/catch`：Host 使用 `BackgroundServiceExceptionBehavior.Ignore`，循环异常必须自行兜底并记 Error，否则清理会静默停止。

### 保留判据与删除路径（`AuditRepository`）

- 截止时间：`DateTime.Now.AddDays(-RetentionDays)`，与审计写入使用 `DateTime.Now` 的时间基准一致；判据是严格 `< cutoff`。
- `IAuditRepository` 新增 `DeleteExpiredMessageAuditsAsync(cutoff)` 与 `DeleteExpiredClientHistoriesAsync(cutoff)`，删除全程持 `_writeLock`，与审计写入互斥。
- 分批策略：先按 `CreatedAt` / `Timestamp` 升序取一批主键（SQLite 500 条，其他提供程序 2000 条），再按主键分块执行 `Deleteable().Where(idChunk.Contains(...))`（单条 SQL 的 IN 参数上限 900）。
- 每批以「本批是否真的删掉行」作为退出条件之一，避免并发写入导致同一批主键被反复选中形成死循环。
- `AutoInitializeSchema=false` 且从未初始化过 schema 时，两个删除方法直接返回 0，不因表不存在报错。

### 空间回收（`AuditRepository.VacuumAsync`）

- 只在 `DbType.Sqlite` 上执行 `VACUUM`，其他提供程序直接返回。
- **刻意在 `_writeLock` 之外执行**：大库 `VACUUM` 需要独占且耗时可观，持锁会把审计写入队列（上限 50000）堵到溢出上限；当前取舍是允许 `VACUUM` 偶发遇到 SQLite 忙锁，失败只记 Warning 并在下一轮清理后重试。
- worker 通过 `_auditRepository is AuditRepository` 判定后调用，`IAuditRepository` 接口本身不暴露 `VACUUM`（它是 SQLite 专有语句）。

### 故障隔离

两张表的清理互相隔离：`RunCleanupOnceAsync` 用 `TryDeleteAsync` 分别执行，单张表失败只记 Error 并返回 0，另一张表仍然清理。这避免「消息审计表持续失败导致客户端历史表也被饿死、继续无界增长」。

## 关键决策

- **新增独立后台任务而不是复用 `MetricsService` 写线程**：清理是分钟级低频动作，放进审计写线程会与追平写入争用；独立任务也便于测试调度计算。
- **不新建第二个 `AuditRepository` / `SqlSugarScope` 实例**：清理复用 DI 单例仓储，避免同一 SQLite 文件上的多实例写入竞争。
- **不用 `Deleteable().Take(n)` 做批量删除**：SQLite 的 `DELETE ... LIMIT` 依赖编译选项 `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`，并非所有构建都启用；「先查主键再按主键分批删除」在所有 `SqlSugar DbType` 上行为一致。
- **`IN` 参数上限取 900**：SQLite 默认 `SQLITE_MAX_VARIABLE_NUMBER = 999`，清理批删必须留出余量，否则大批量删除会以 `too many SQL variables` 失败。
- **`CleanupAtHour` 留空走间隔模式，而不是两个时刻都必填**：默认每天 03:00 保证清理时刻稳定可预期，同时保留「按间隔兜底」的配置路径；间隔上限由校验强制，不能配成超过 24 小时。
- **Dashboard 累计计数不因清理回落**：`MetricsService.InitializeDashboardCountersFromAuditAsync` 的基线只在启动时读取一次，清理不回改它。清理后 Dashboard 累计总数仍为历史总量，审计列表只剩保留窗内的数据；该口径已在 README 说明。
- `MessageArchiveThreshold` / `ClientHistoryArchiveThreshold` 的启动迁移提示保留，定位为清理之外的规模提示，不触发额外删除。

## 边界

- 保留窗口按行创建/事件时间判断（`message_audit.CreatedAt`、`client_connection_history.Timestamp`），不按 `UpdatedAt`；长生命周期消息的终态会随其首收时间一起被删除。
- 进程未运行的时间段没有清理，由下一次启动的立即清理收敛。
- 系统时钟被向前调整时按新的本地时间重新计算，最坏情况延后到下一个整点。
- 「每天至少一次」只在进程存活时由调度保证；`RetentionDays=0` 关闭清理时审计数据无界增长，需要运维手工维护。
- 不提供手工触发清理的 HTTP API、按天分区或归档导出；需要线上立即回收空间时通过重启服务触发启动清理。
- 死信目录保留（`Reliability:DeadLetterRetentionDays`）与 Serilog 日志保留（`Serilog:RetentionDays`）是各自独立的配置，本次未改动。
