# 2026-10-01 投递延迟根因修复（消费者专用线程 + 审计读并发上限 + 运行期指标）

## 背景

1000 msg/s × 60s 压测下出现投递延迟尾部抖动：60000 条消息全部投递成功（0 失败 / 0 重试 / 0 死信），
但 2877 条（4.8%）端到端延迟超过 500ms，最大 3519ms；每秒日志行数显示消费者有约 1.3 秒的处理亏空后补账。

## 定位结论（实测事实）

审计记录与毫秒级日志时间戳拆解延迟分布：

| 事实 | 数值 |
| --- | --- |
| 延迟落在「入队 → 消费者取件」 | 100%，最大 3519ms |
| 延迟落在「取件 → 发布完成」 | 最大 2ms |
| 抖动窗口内 Broker 入队速率 | 稳定 1000/s，未受影响 |
| 日志时间戳断层 > 300ms | 0 次（排除整进程冻结） |
| Time paused by GC（90s 采样） | 合计 57.9ms，单秒最大 12ms（排除 GC 停顿） |
| ThreadPool Queue Length（稳定压测） | 最大 4 |
| ThreadPool Thread Count（稳定压测） | 5 → 20（= 逻辑核数） |

消费者取件路径的唯一线程池依赖点：`InMemoryMessageQueue` 使用默认 `BoundedChannelOptions`
（`AllowSynchronousContinuations = false`）。被挂起的 `ReadAllAsync` 消费者由写者唤醒时，
其续体作为线程池工作项排队，必须等到空闲的线程池线程才能继续；Broker 接收路径跑在 socket
接收循环（IOCP 完成线程）上，因此呈现「入队正常、取件掉队」的形状。

用服务公开 API 主动复现（隔离实例、1000 msg/s 压测中并发打 96 个 `/api/messages`，审计库 188MB）：

| 指标 | 冲击前 | 冲击时 |
| --- | --- | --- |
| ThreadPool Completed Work Item Count | 5921/s | 781/s |
| ThreadPool Thread Count | 17 | 37 |
| Monitor Lock Contention Count | 2661/s | 5216/s |
| 投递延迟 p99 / max | ~1ms | 313ms / 378ms |

把 `ThreadPool.MinThreads` 抬到 200 后重复同一冲击：p99 301ms / max 363ms，无改善，
说明瓶颈是线程池线程被阻塞型工作占住，而非线程创建速度。

两次严重停顿（3519ms、2327ms）发生在 counters 采集窗口之外，未取到当时的直接证据，
其形状与上述机制一致（100% 等待、发布 ~1ms、无 GC、无冻结）。

## 本次改动

### 1. 投递消费者改用专用线程 + 同步阻塞取件

- `IMessageQueue` 增加 `TryDequeueBlocking(out ForwardMessage? message, CancellationToken)`：
  真正的同步阻塞取件，只允许在专用线程上调用。
- `InMemoryMessageQueue` 增加 `SemaphoreSlim _itemsAvailable` 作为取件信号：每次成功入队释放一个信号，
  消费者在专用线程上 `Wait` 该信号后被直接唤醒，不产生线程池续体。
  信号与真实条目数不一致时（排空路径用 `TryDequeueAsync` 取走消息会留下多余信号）只会造成一次
  无效唤醒并回到等待，既不空转也不丢唤醒。
- `MessageDeliveryService` 的消费循环由 `async Task ConsumeLoopAsync` 改为同步 `ConsumeLoop`，
  单条消息处理以 `GetAwaiter().GetResult()` 同步等待；消费者经新增的 `StartConsumerThread` 用
  `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning, TaskScheduler.Default)` 启动，
  由调度器创建专用线程而不是占用线程池线程。
- `MetricsMessageQueue` 装饰器同步透传 `TryDequeueBlocking`，保持队列装饰链完整。
- `_consumerTasks` 类型、停机排空、动态扩缩容逻辑未改动（`LongRunning` 同样返回 `Task`）。

### 2. Web 管理面审计读查询并发上限

- `AuditRepository` 新增 `MaxConcurrentReads = 4` 与 `_readGate` 闸门，作用于全部读路径：
  `GetMessageByIdAsync`、`GetPagedMessagesAsync`、`GetPagedClientHistoryAsync`、
  `GetDashboardMessageSummaryAsync`。
- 写路径（`RecordMessageAuditAsync` 与批量落库）和清理路径（`DeleteExpired*Async`）不经过该闸门，
  避免影响正常审计落库。

### 3. 运行期指标

- `MetricsService` 新增 `BuildRuntimeSnapshot(Process?)`，`/api/metrics` 与降级快照都输出 `runtime` 段：
  逻辑核数、`ThreadPool.ThreadCount`、`PendingWorkItemCount`、`CompletedWorkItemCount`、
  Gen0/1/2 回收次数、`GC.GetTotalPauseDuration()` 累计停顿毫秒、GC 堆大小、进程累计 CPU 毫秒。
- 每一项单独兜底，取值失败记为 -1，不允许影响 Dashboard 接口。
- 该段的用途是在故障现场自证资源瓶颈：以 LocalSystem 运行的 Windows 服务不允许外部 profiler 附着
  （本轮定位即因此只能依赖隔离实例采集 counters）。

### 4. 逐条消息日志降级到 Debug

- `MqttBrokerHost.OnInterceptingPublishAsync` 的「已入队」与 `MessageDeliveryService.ProcessMessageAsync`
  的「开始处理」「注入成功」由 `LogInformation` 改为 `LogDebug`。
- 依据：1000 msg/s 下逐条 Information 产生约 26MB/小时日志（60000 条消息对应 180103 行），
  `Serilog.Sinks.File` 每条都在同一全局锁上写入，实测 `Monitor Lock Contention Count` 稳定在 2200~2700 次/秒。
- 实测降级效果（同一二进制、15000 条消息）：日志文件从 8.88MB / 60088 行降到 13KB / 88 行（仅启动与连接事件）。
- 实测降级收益（同一负载）：投递延迟 avg 从 6.65ms 降到 0.22ms、p99 从 91.28ms 降到 0.74ms，
  说明逐条日志的写入竞争本身就是延迟来源。
- 逃生通道：`Serilog:MinimumLevel:Override` 里给这两个类别配 `Debug` 即可恢复逐条日志（无需改代码），
  恢复后为每条消息 4 行（该类别内还有一条 Debug 的「注入 Topic 成功」）。

## 明确不做

- 不调整 `ThreadPool.MinThreads`：已验证（1000 msg/s + 96 并发审计查询）抬高下限无改善（378ms → 363ms）。
- 不改动 `Serilog` 逐条 Information 日志：日志量（3 行/消息）与锁竞争（2200~2700 次/秒）已记录在案，
  属独立议题。
- 不把 `ProcessMessageAsync` 内部改为全同步：其内部续体未观测到延迟（发布耗时最大 2ms）。

## 边界条件

- 消费者专用线程数量等于投递并发度（默认 3，运行期受 `ReliabilityOptions.MaxConcurrencyHardLimit` 约束），
  每个消费者一条专用线程，不占用线程池线程。
- 运行期把并发度下调到低于消费者数量时，多余消费者会等待并发槽位，该等待仍经过线程池续体；
  这是运维主动限流的预期行为。
- 消费循环内 `ThroughputController.WaitAsync` 在启用速率限制时会 `Task.Delay`，其续体同样经过线程池；
  速率限制本身是限流语义，不影响无限流路径的取件延迟。
- `AuditRepository` 读闸门只限制并发数（固定 4），不改变单次查询耗时；超过上限的请求排队等待。
- `TryDequeueBlocking` 只能在专用线程上调用；在 MQTT 事件回调或线程池线程上调用会造成线程池饥饿。
